## 1. copy モード（#13）

### 1.1 目的

dotfiles の配置には、シンボリックリンクを張る方法と、ファイルの実体をコピーする方法がある。v0.2.0 まではシンボリックリンクだけを扱ってきた。v0.3.0 では、どちらで配置するかを利用者が選べるようにする。

copy を選ぶのは、次のような場合を想定している。

- リンクを作る権限がない環境（Windows など）。
- リンクではなく実体のファイルを求めるアプリがある。

### 1.2 設定

```toml
[general]
mode = "symlink"   # "symlink" または "copy"
```

| キー | 型 | 既定値 | 意味 |
| --- | --- | --- | --- |
| mode | 文字列 | `"symlink"` | 配置の方法。`"symlink"` はリンクを張り、`"copy"` は実体をコピーする |

- `[general]` は v0.2.0 で加えたテーブル（v0.2 の 8.5）である。`mode` を省略すると `"symlink"` になり、v0.2.0 と同じに動く。
- `"symlink"` と `"copy"` 以外の値はエラーにする。
- v0.2.0 の dots は、`[general]` の中の未知のキーをエラーにする。そのため、`mode` を書いた dots.toml は v0.2.0 では読めない。
- 粒度はグローバルだけとする。エントリごとや OS ごとに上書きできるかは未決である（1.12）。記録はファイルごとに持つので、後から広げられる。
- Windows でも、自動では copy に切り替えない。リンクを作る権限がなくて失敗したときに、エラーメッセージで `mode = "copy"` を案内する。

### 1.3 state

#### 記録するもの

- symlink は、v0.2.0 と同じく `links` に記録する。stale を検出するのに必要なためである（v0.2 の 5.2）。
- copy で置いたファイルは、ユーザーが自分で置いたファイルと見分けがつかない。そのため、copy で置いたファイルについては、配置したときのハッシュを記録する。
- 前回の mode は記録しない。mode を切り替えたことは、各配置先の今の状態と記録から分かる（1.6）。
- 初めて apply するときは、既存のファイルがあるかどうかを記録からは知れない。そのため、v0.2.0 と同じくファイルシステムを直接調べる処理も続けて使う。

#### 形式（案）

v0.2 の 5.2 の方針どおり、`version` は上げず、`copies` キーを足す。v0.2.0 の statefile は知らないトップレベルのキーを残したまま書き戻すので、v0.2.0 の dots で apply しても `copies` は失われない。

```json
{
  "version": 1,
  "links": [],
  "copies": [
    {
      "target": "/home/user/.gitconfig",
      "kind": "file",
      "hash": "sha256:…",
      "repository": "/home/user/dotfiles",
      "source": "gitconfig",
      "recorded_at": "2026-10-13T12:00:00Z"
    },
    {
      "target": "/home/user/.config/nvim",
      "kind": "dir",
      "repository": "/home/user/dotfiles",
      "source": "config/nvim",
      "recorded_at": "2026-10-13T12:00:00Z"
    }
  ]
}
```

| キー | 内容 |
| --- | --- |
| copies[].target | 配置先の実行時の絶対パス |
| copies[].kind | `file`（コピーしたファイル）または `dir`（コピーするときに dots が作ったディレクトリ） |
| copies[].hash | `file` のとき、配置した内容の SHA-256 |
| copies[].repository | 記録したときのリポジトリルートの絶対パス |
| copies[].source | リポジトリルートからの source の相対パス（/ 区切り）。表示に使う |
| copies[].recorded_at | 記録した UTC 日時（RFC 3339） |

#### 規則

- 1つの target の記録は、`links` と `copies` を合わせて1つだけにする。片方に記録するときは、もう片方から消す。
- ディレクトリをコピーした場合は、ファイルごとに記録して判定する。ディレクトリ全体を1つのハッシュにまとめると、`.DS_Store` や `lazy-lock.json` が置かれただけでドリフトと判定され、apply が毎回止まってしまう。記録にないファイルは無視する。
- コピーするときに dots が作ったディレクトリも `kind: "dir"` として記録する。clean で、空になったディレクトリを消すときに使う（1.9）。
- target どうしの比較は v0.2.0 と同じく `pathx.Key` で行う。Windows と macOS では大文字と小文字を区別しない。
- ハッシュを計算する前に Lstat で通常ファイルかどうかを確かめ、リンクはたどらない。リンクをたどってハッシュを計算すると、source を指すリンクが「実体が source と同一」と判定され、コピーとして記録されてしまう。
- 書き込みは、v0.2.0 と同じく一時ファイルに書いてから rename で置き換える。記録ファイルを失った場合や、コピーした直後に dots が落ちた場合は、次の apply で「実体が source と同一なら記録して終わり」の規則（1.4）によって元に戻る。

### 1.4 apply の判定（mode = copy）

配置先ごとに、今の mode を前提として判定し、通常の apply の計画として扱う。mode を切り替えたときのための移行処理は別に持たない。

| 配置先の状態 | 動作 | 確認 |
| --- | --- | --- |
| 存在しない | コピーする | なし |
| source を指す正しいリンク | コピーで置き換える | なし |
| 別の場所を指すリンク | 管理外の既存ファイルとの衝突として扱う（既存の流れ） | あり |
| 実体が source と同一 | 何もしない。記録だけ更新する | なし |
| 実体が記録と同一で、source とは異なる | 上書きして更新する | なし |
| 実体が記録とも source とも異なる | ドリフト（1.5） | 中断 |
| 記録がなく、実体が source と異なる | 管理外の既存ファイルとの衝突として扱う（既存の流れ） | あり |

- dots が置いたもの（正しいリンクや、変更されていない記録済みのコピー）を更新したり置き換えたりするときは、確認もバックアップもしない。
- 記録があるのに source から消えたファイルは、stale として扱う（1.9）。apply は削除もしないし、ドリフトとして中断もしない。v0.2.0 の「apply は stale を消さない」に合わせる。
- 配置先が別のボリュームにある場合、copy モードでは `state.Evaluate` の `ErrCrossVolume`（相対リンクを作れない）をエラーにしない。

### 1.5 ドリフト

ドリフトとは、copy で置いたファイルが、そのあとアプリなどによって環境側で変更されたものをいう。

- 判定の条件: 実体が記録と異なり、**かつ**実体が今の source とも異なるとき、ドリフトとする。
- 実体が今の source と同一なら、ドリフトでも衝突でもない。記録を更新するだけにする。
- copy のまま再び apply する場合も、copy から symlink に切り替える場合も、同じ条件で判定する。
- 確認プロンプトを出す前に判定する。1件でもドリフトがあれば、TTY の有無にかかわらず何も聞かず、何も変更せずにエラー終了する。dots は内容の調停をしない。
- 利用者は、変更をリポジトリに取り込むか、環境側のファイルを退避または削除すれば解消できる。どちらでも次の apply が通る。
- 中断したときの一覧は、衝突の種類ごとに分けて表示する。「前回の apply 以降に変更された（modified since last apply）」と「dots が管理していない（not managed by dots）」とでは、利用者が取るべき対処が違うためである。
- `--no-confirm` や `--overwrite` のような、上書きを強制するフラグは設けない。

管理外の既存ファイルとの衝突は、これまでの流れのまま扱う。TTY があれば確認し、Yes ならバックアップを取ってから置き換える。TTY がなければ一覧を表示し、何も変更せずにエラー終了する。

### 1.6 mode の切り替え

#### symlink から copy へ

切り替える前は、配置先は source を指すリンクで、`links` に記録がある。

| 配置先の状態 | 動作 | 確認 |
| --- | --- | --- |
| source を指す正しいリンク | コピーで置き換える | なし |
| 別の場所を指すリンク | 管理外の既存ファイルとの衝突として扱う（既存の流れ） | あり |
| 存在しない | コピーする | なし |
| 実体が source と同一 | 記録だけ作る | なし |
| 記録がなく、実体が source と異なる | 管理外の既存ファイルとの衝突として扱う（既存の流れ） | あり |

- 記録は `links` から消し、`copies` に移す。
- ディレクトリへのリンクは、実体のディレクトリに置き換える。中のファイルを1つずつコピーし、ファイルごと、ディレクトリごとに記録する。ディレクトリはリンクの上に rename で直接置き換えられない。そのため、隣に一時ディレクトリを作って中身をそろえ、リンクを消してから rename する。リンクを消してから rename するまでのごく短い間は、配置先が存在しない。
- リンクで配置していた間にアプリが書き込んだファイル（`lazy-lock.json` など）は、実際にはリポジトリ側に作られている。それらは source の一部なので、管理対象としてコピーする。
- リンクには中身がないので、ドリフトは起こらない。そのため、ほとんどの場合は確認なしで進む。

#### copy から symlink へ

切り替える前は、配置先は実体で、`copies` に記録がある。

| 配置先の状態 | 動作 | 確認 |
| --- | --- | --- |
| 実体が source と同一 | リンクで置き換える | なし |
| 実体が記録と同一で、source とは異なる | リンクで置き換える | なし |
| 実体が記録とも source とも異なる | ドリフト（1.5） | 中断 |
| 記録がなく、実体が source と異なる | 管理外の既存ファイルとの衝突として扱う（既存の流れ） | あり |
| 存在しない | リンクを作る | なし |

- 記録は `copies` から消し、`links` に移す。
- ディレクトリでは、中のファイルが1つでもドリフトしていれば中断する。
- ドリフトがなくても、ディレクトリに記録にないファイル（`lazy-lock.json` など）があると、リンクで置き換えたときにそのファイルが消える。この場合に限り、既存の流れ（確認してバックアップを取る）で扱う。記録にないファイルがなければ、確認せずに置き換える。
- 置き換えたら、配下のファイルとディレクトリの記録をすべて消し、ディレクトリへのリンクを1件だけ記録する。

### 1.7 書き込みの手順

- ファイルのコピーは、同じディレクトリに一時ファイルとして書いてから、rename で配置先に置き換える。rename はリンクそのものを置き換え、リンク先はたどらない。この手順なら、配置先がリンクのままでも、リンク先の source に書き込んでしまうことがない。
- ディレクトリの置き換えは 1.6 のとおりとする。

### 1.8 手放したファイルを再び登録する場合

clean で手放した（Release した、1.9）ファイルについて、後で同じルールを dots.toml に戻して apply した場合を考える。このときは記録がないので、1.4 の「記録がない」場合の扱いになる。

- 実体が source と同一なら、記録だけ作る。
- 実体が source と異なれば、管理外の既存ファイルとの衝突として扱う。TTY があれば確認してバックアップを取ってから置き換え、なければ一覧を表示してエラー終了する。

手放したファイルに加えた変更が、知らないうちに上書きされることはない。「以前 dots が手放したファイル」であることを記録に残して特別に案内する案は採らない。手放したあとも記録を持ち続けることになり、「Release したら記録を消す」という意味と食い違うためである。（検討中。#13 で合意したら確定する）

### 1.9 dots clean

#### stale の判定

copy で置いたファイルの記録が stale かどうかは、v0.2 の 5.4 と同じ条件で判定する。つまり、記録の repository が今のリポジトリと同じで、記録の target が今の設定から展開した配置先に含まれないものを stale とする。記録はファイルごとに持つので、次のどちらの場合も stale になる。

- ルールそのものを dots.toml から消した場合。
- ルールは残したまま、source のディレクトリからファイルを消した場合。

stale になった理由によって扱いを分けることはしない。どちらの場合も同じ確認で扱う。

stale なコピーは、配置先の今の状態によって次のように分ける。

| 状態 | 条件 | clean での動作 |
| --- | --- | --- |
| StaleCopy | 通常ファイルで、ハッシュが記録と一致する | 確認で選んだとおりにする（Remove または Release） |
| StaleCopyChanged | ハッシュが記録と違う、またはリンクやディレクトリになっている | 触らない。記録を消し、`! kept` で報告する |
| StaleGone | 存在しない | 記録を消す（表示はしない） |

#### 確認

最初に全体の一覧を表示し、そのあと**リンク → コピー**の順に、対象があるものだけ確認する。

| 確認 | 選択肢 | 初期カーソル |
| --- | --- | --- |
| stale なリンク（StaleLink） | No – keep / Yes – remove | No |
| stale なコピー（StaleCopy） | Release – keep the files, stop managing them / Remove – delete the files | Release |

- No を選んだリンクは、stale のまま残る。記録は消さない。
- コピーの選択肢には「何もしない」を設けない。後で決めたいときは中断すればよい。clean を実行しなければ stale のまま残る。
- Release は、実体を残して記録だけを消す（管理をやめる）。Remove は削除する。
- 選んだ動作は、その種類の stale すべてに適用する。一部だけ消したいときは、Release したあとで自分で `rm` する。この方法は README に書く。
- 回答がすべてそろってから実行する。途中で中断したら何も変更せず、終了コードは130とする。
- `--no-confirm` は設けない（1.10）。TTY がなく確認が必要な場合は、一覧を表示し、何も変更せずにエラー終了する。確認がいらない処理（StaleCopyChanged や StaleGone の記録を消すだけのもの）は、TTY がなくても実行する。

#### 削除の手順（Remove）

- 削除する直前にハッシュを計算し直す。確認プロンプトを待っている間に、アプリがファイルを書き換えることがあるためである。v0.2 の 7.2 で、削除の直前に Lstat と Readlink をやり直すのと同じ理由である。ハッシュが変わっていれば削除せず、StaleCopyChanged と同じく `! kept` とする。
- ディレクトリをコピーしていた場合は、記録のあるファイルを消してから、空になった `kind: "dir"` のディレクトリを下の階層から順に消す。
- 管理外のファイルが残るディレクトリは消さず、記録だけ消す。そのことは確認の前の一覧で示し、終了時にも `! kept` で表示する。
- バックアップは取らない。

#### 表示

```
Repository: ~/dotfiles

Links
  - stale ~/.config/tmux  ← config/tmux
Copies
  - stale ~/.gitconfig     ← gitconfig
  - stale ~/.config/nvim   ← config/nvim
    keeps 2 files not managed by dots
  ! changed ~/.zshrc
    changed since dots copied it; dots will not remove it

Remove 1 stale link?
> No – keep it
  Yes – remove it

What should dots do with 2 stale copies?
> Release – keep the files, stop managing them
  Remove – delete the files
```

終了時には、削除しなかったものとその理由を表示する。

```
  ! kept ~/.config/nvim
    2 files not managed by dots were left in place
  ! kept ~/.zshrc
    changed since dots copied it; not removed and no longer managed
```

- 変更されていたために削除しなかったコピーと、管理外のファイルが残ったディレクトリは、どちらも `! kept` で表示する。dots が削除しなかったので、必要なら利用者が自分で片付ける、という点が共通しているためである。
- リンクの StaleChanged は、v0.2.0 のとおり `! skipped` のままにする。

### 1.10 clean の `--no-confirm` を削除する

clean から `--no-confirm` を削除する。

- 理由: コピーの確認を Release / Remove の2択にすると、`--no-confirm` のときにどちらを選ぶかが決まらない。どちらを既定にしても、上書き用のフラグを設けない方針（1.5）とぶつかる。
- TTY がなく確認が必要な場合は、apply と同じく一覧を表示し、何も変更せずにエラー終了する。
- clean は、ルールを消したあとにたまに実行するコマンドである。スクリプトから自動で実行する必要は薄い。apply は stale を消さないので、自動化には影響しない。
- 影響する箇所: `internal/cli/clean.go`、`clean_test.go`、`.github/scripts/smoke.sh`、README、v0.2 の仕様書の 3章、7.1、7.3、10章。smoke.sh では、`--dry-run` と「TTY がなければエラー終了する」ことを確認する形に変える。

### 1.11 README に書く制限

- リポジトリを移動したあと、apply をしないままルールを消すと、移動前の記録は stale として検出できない（v0.2 の 5.4）。この制限はリンクでも同じである。ただしリンクは移動するとリンク切れになるので気づけるが、copy モードではリンク切れが起きないので気づきにくい。リポジトリを移動したら、一度 apply すること。
- clean で一部のコピーだけを消したいときは、Release したあとで自分で `rm` する。

### 1.12 未決事項

- 「更新」操作の表示記号。既存の `~` は「バックアップを取ってから置き換える」を意味する。バックアップを取らない置き換えや更新には、別の記号が要る。
- copy モードで、source やディレクトリの中にシンボリックリンクがある場合の扱い。検証エラーにするか、リンク先の実体をコピーするか。
- mode の粒度。グローバルだけにするか、エントリごとや OS ごとの上書きを許すか。
- 途中で失敗した場合に、記録をいつ更新するか。エントリごとか、最後にまとめてか。
- Release した項目の表示（記号と短い語）。
- status で、ドリフトしたコピーと stale なコピーをどう表示するか。
- コピーするときに、ファイルの権限（実行ビットなど）を引き継ぐか。

### 1.13 先行ツールとの比較

#13 の議論のときに、Gemini で調べた結果である。

- 「管理をやめる」と「消す」を分けるツールがある。chezmoi は `forget` と `destroy`、yadm は `rm --cached` と `rm` で分けている。dots の Release / Remove は、この2つを1つの確認にまとめた形である。
- 空になったディレクトリだけを消し、管理外のファイルが残るディレクトリは残す。Stow、rcm、dotter、chezmoi、home-manager に共通する挙動である。
- source からファイルを消したときに配置先から自動で消すかどうかは、ツールによって分かれる。chezmoi、Stow、rcm、dotbot は消さない。dotter、home-manager、yadm は消す。dots は clean で確認してから消すので、その中間にあたる。
- コピーした内容を記録してドリフトを検出する点は、chezmoi（bbolt DB に SHA-256 を記録）や dotter（キャッシュと比べる）と同じである。
- clean に `--force`（変更されたコピーも消す）を加える案は採らない。上書き用のフラグを設けない方針に反するためである。

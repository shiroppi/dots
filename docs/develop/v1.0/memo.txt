## 2. 環境変数 (environment) 管理の設計方針

* **基本要件:** root権限（`sudo`）を要求する `/etc/environment` は使用せず、ユーザー権限（User-level）で完結させるつもり？。sudoを使うか使わないか未定
* **最大の課題:** TOMLからキーが「削除」された際の状態追従（ドリフト解決）。
* **OSごとの最適解（GUIアプリへの適用も含む場合）:**
* **Linux:** `~/.config/environment.d/*.conf` を完全上書き生成（Systemdが自動適用するため状態管理不要）（ただし環境依存）。
* **macOS:** `launchctl setenv` ＋ LaunchAgentの自動生成（削除追従のために State 管理が必要）。
* **Windows:** レジストリ `HKCU\Environment` への直接書き込み（削除追従のために State 管理が必要）。



**▼ 具体的な記法（environment.toml または dots.toml内）**

```toml
# 全OS共通の環境変数
[environment]
editor = "nvim"
lang = "ja_JP.UTF-8"

# OSごとの上書き・追加
[environment.darwin]
apple_id = "3219083"

[environment.windows]
microsoft_id = "2131313"

```

## 3. Git設定 (gitconfig) 管理の設計方針

.gitconfigを作らせて参照するほうがカバ＝レッジは広そうだけど、dots内で新たにキーを設定して簡潔させたい。（要議論）

-------------------------めも-----------------------------------------
* **基本要件:** OSごとの差異（credential.helper等）や用途ごとの差異を吸収する。
* **解決策:** `dots`側でGitのINIパーサーやコマンド実行ロジックを独自実装して複雑化させるのではなく、**Gitのネイティブ機能 (`include` / `includeIf`) とSymlinkを組み合わせる**アプローチを採用。

**▼ 具体的な記法（dots.toml側：Symlinkの定義）**

```toml
# 共通の.gitconfigをリンク
[dots]
"~/.gitconfig" = "git/.gitconfig"

# OS固有のGit設定を、特定の名前（_os）でリンク
[dots.darwin]
"~/.gitconfig_os" = "git/mac.gitconfig"

[dots.windows]
"~/.gitconfig_os" = "git/windows.gitconfig"

```

**▼ 具体的な記法（git/.gitconfig側：Gitネイティブの読み込み設定）**

```ini
[user]
    name = user
    email = user@example.com

# リンク先のOS固有ファイルが存在する場合のみ読み込まれる（エラーにならない）
[include]
    path = ~/.gitconfig_os

```

## `dots` のプラグイン構想

### 1. 基本思想

`dots` は **dotfiles管理に必要な最小限のコア**だけを持つ。

```text
dots
├── config
├── deploy
├── platform
└── profile
```

その上で、追加機能はプラグインとして提供する。

```text
dots
├── core
└── plugins
    ├── source
    ├── bootstrap
    └── ...
```

つまり、

> **dots = dotfiles manager + 拡張可能なプラットフォーム**

という位置づけ。

---

### 2. `source` はプラグインの第一号

今回考えていた `source` は、

> 外部リポジトリから必要な設定・スクリプトなどを取り込む

ための機能。

例えばOmarchyから一部だけ持ってくる。

```toml
[[source]]
name = "omarchy-agent-usage"
repository = "https://github.com/omacom/omarchy"
path = "bin/omarchy-agent-usage-claude"
```

これを `source.dots` というプラグインとして実装する。

---

### 3. 実装方式はGoのpluginではなく外部プロセス

Goには `plugin` パッケージがありますが、これはWindows対応などを考えると不向き。

そこで **GitHub CLIのextension方式**を参考にする。

```text
dots
  ↓
source.dots
```

`source.dots` は普通の実行ファイル。

```text
~/.local/bin/
├── dots
├── source.dots
└── bootstrap.dots
```

`dots` が `source.dots` を発見して起動する。

---

### 4. gh CLIとの関係

かなり `gh` に近い。

```text
gh foo
 ↓
gh-foo
```

```text
dots source
 ↓
source.dots
```

ただし思想としては少し違う。

`gh` のextensionは主に**新しいCLIコマンドを追加するもの**。

一方 `dots` のpluginは、

> **dotsそのものに新しい能力を追加するもの**

にしたい。

例えば、

```text
dots
├── core
├── source plugin
├── bootstrap plugin
├── secrets plugin
└── ...
```

という感じ。

---

### 5. プラグインAPIは最初は極小でいい

最初から巨大なplugin frameworkを設計しない。

まずは、

```text
dots
 ↓
プラグインを探す
 ↓
実行する
 ↓
引数を渡す
```

だけ。

必要になったら後から、

- 設定へのアクセス
- hooks
- events
- JSON/RPC
- plugin metadata
- lifecycle

などを追加する。

---

## 最終的なイメージ

```text
                  dots
                   │
          ┌────────┴────────┐
          │      Core       │
          │                 │
          │ config          │
          │ deploy          │
          │ platform        │
          │ profile         │
          └────────┬────────┘
                   │
              Plugin API
                   │
       ┌───────────┼───────────┐
       ↓           ↓           ↓
    source     bootstrap    other
       │
       ↓
 外部dotfiles / scripts
```

これなら **「ユーザーのdotfiles構造を矯正しない」**という `dots` の思想とも噛み合います。

**Coreは小さく、必要な能力だけユーザーが追加する。**

その意味で、`source` を単なる機能として本体に詰め込むより、**「dotsをNeovimのような拡張可能な基盤にする」**という発想の方が面白いと思います。
